# Архитектура мастерской устройств

Мастерская — настольное приложение на Rust для моделирования устройств, например экзоскелета,
третьей руки или очков с сенсорами. Симуляция выявляет нарушения и открытые обязательства
до решения об изготовлении.

Главный принцип: **идеальной симуляции нет ни у кого**. Доверие к числам держится на четырёх
вещах, и архитектура построена вокруг них:

1. **Проверенная модель для каждой области** с явно записанными допущениями.
2. **Связка моделей** между собой (механика ↔ привод ↔ батарея ↔ прочность ↔ тело).
3. **Проверка вторым независимым способом**: ручной расчёт или другая модель всегда стоит
   рядом с результатом симуляции, расхождение показывается, а не прячется.
4. **Запас прочности 2–4×** для всего, что касается тела, и испытание на стенде.

## 1. Слои

│ workshop (Bevy + egui)  — окно, 3D, свободная камера, панели сверки  │
├──────────────────────────────────────────────────────────────────────┤
│ sim-scenarios — устройства: модель + управление + сверки + выводы    │
│   (ко-симуляция «прошивка ↔ мотор ↔ локоть ↔ батарея ↔ радио ↔ среда»)│
├──────────┬─────────┬──────────┬──────────┬──────────┬────────────────┤
│ sim-core │ sim-fem │ sim-em   │ sim-env  │ sim-radio│ sim-circuit    │
│ механика │ прочн.  │ поля,    │ воздух,  │ Wi-Fi/BLE│ схемы (MNA),   │
│          │         │ магниты, │ вода,    │ тело,    │ батарея, платы │
│          │         │ мотор    │ человек  │ вода     │                │

| `sim-circuit` | схемы: разбор SPICE-подмножества, MNA, Ньютон с ограничением p-n переходов, трапеции; пошаговый режим для ко-симуляции; Li-ion ячейка (эквивалентная схема); KiCad, расчёты плат по IPC-2221 и инженерная ЭМС (§8.4) | `nalgebra`, `sim-verify` |
| `sim-mcu` | прежний виртуальный ABI: RV32IMC + Zicsr, прерывания, `wfi`, периферия и ELF; контракт прошивки экзо (`exo`). Регистровая модель ESP32-C3 находится в `sim-boards` (§8.4) | `sim-verify` |
| `firmware/` (отдельный workspace) | прошивки на Rust `no_std` под `riscv32imc-unknown-none-elf`: `vmcu-hal`, `selftest`, `exo-ctrl` (контроллер локтя: контур тока 10 кГц, угла 1 кГц, защиты); собранные ELF — в `assets/firmware/` | — |
| `workshop` | приложение: Bevy-сцена, свободная камера, egui-панели (редактор текста, кнопки действий, журнал UART, несколько графиков), съёмка без экрана | все выше + `bevy`, `bevy_egui`, `egui_plot` |

Физика ничего не знает о графике: `cargo test` гоняет всё ядро без окна и без GPU.
Окно ничего не знает о физике конкретного устройства: оно рисует то, что отдаёт
сценарий (геометрия, стрелки, кольца, цифры, сверки, график).

## 2. Решения по стеку и почему

### 3D и окно — Bevy 0.20 + bevy_egui 0.43 + egui_plot

* **Bevy** (MIT/Apache-2.0) — самый живой 3D-движок на Rust: PBR и тени, Metal на M1 из
  коробки (через wgpu), загрузка glTF (понадобится для CAD-моделей устройств), гизмо для
  стрелок сил и моментов, ECS для сотен объектов в сценах. Съёмка кадра встроена.
* Включены только фичи `3d` (без аудио, 2D-спрайтов, UI-виджетов Bevy) — меньше сборки.
* **egui** (MIT/Apache-2.0) для панелей: таблицы сверки, ползунки, графики пишутся в
  десятки строк, а не в сотни, как в UI самого Bevy. Встроенные шрифты egui покрывают
  кириллицу; для математических знаков подключается системный Arial Unicode.
* Рассматривали: `three-d` (легче, но беднее экосистема), голый `wgpu` (всё руками),
  Fyrox (меньше сообщество). Bevy выигрывает тем, что «мастерской» дальше понадобятся
  импорт моделей, выбор объектов мышью, несколько окон — всё это в Bevy уже есть.
* Цена решения: первая сборка ~7 минут и ~8 ГБ в `target/`, Bevy ломает API раз в
  ~3–4 месяца. Поэтому вся физика вынесена в отдельные crate без Bevy — обновление
  движка графики не трогает проверенную физику.

### Механика — своё ядро на Rust по Featherstone

Почему своё, а не Rapier/MuJoCo прямо сейчас:

* Нужен **точный момент в каждом шарнире** — это главный выход для экзоскелета.
  Игровые движки (Rapier, PhysX, Bullet) считают импульсами в итерационном решателе;
  момент из них достаётся приблизительно. RNEA/ABA дают его точно и по определению.
* Алгоритмы Featherstone — стандарт отрасли: те же RNEA/ABA/CRBA внутри MuJoCo, Drake,
  Pinocchio, RBDL, Simbody. Поэтому наше ядро **напрямую сверяемо** с ними на одинаковых
  моделях (этап 2), а не «похоже на».
* Ядро маленькое (~1000 строк вместе с тестами), читаемое и целиком покрыто тестами против аналитики.
* `nalgebra` (Apache-2.0) — линейная алгебра.

Соглашения как у MuJoCo/Drake: Z вверх, X вперёд, Y влево; вектор движения `[ω; v]`,
вектор силы `[n; f]`. Окно переводит в Y-вверх Bevy одним поворотом.

Управление и внешние силы держатся постоянными на шаге (zero-order hold) — так работает
цифровой регулятор мотора. Регулятор экзоскелета — ПИД на 2 кГц, траектория подъёма —
минимального рывка (Flash & Hogan, 1985), как двигается рука человека.

### Внешние проверенные движки — сначала вызываем, потом (может быть) переписываем

Правило: **проверенный движок сначала зовём как есть**, на Rust переписываем только то,
что окупается (нужно в реальном времени, нужна точная интеграция с ядром), и только
с тестами против оригинала на одинаковых входах.

Как звать:

| Способ | Когда | Лицензионно |
|---|---|---|
| **Отдельный процесс** + файлы/stdin (`.inp` → CalculiX, `.cir` → ngspice, `.osim` → OpenSim CLI, скрипт → PyBaMM) | GPL-пакеты; тяжёлые расчёты не в реальном времени | безопасно для GPL: наш код не линкуется с их кодом |
| **FMI 2.0/3.0 (FMU)** — ко-симуляция | модели систем из OpenModelica, Simulink-подобные цепочки «батарея → мотор → редуктор» | стандарт открыт, FMU несёт свою лицензию |
| **FFI** (C API через `bindgen`) | permissive-библиотеки, которые нужны в цикле реального времени (MuJoCo, ngspice-shared, Cantera) | только для MIT/BSD/Apache/LGPL (LGPL — динамически) |
| **preCICE** | связка двух решателей полей (жидкость ↔ конструкция, нагрев ↔ деформация) | LGPL-3.0, динамическая линковка |

GPL-код (CalculiX, Code_Aster, KiCad, LAMMPS, QEMU, OpenFOAM) **не копируем в ядро и не
линкуем** — только внешний процесс и обмен файлами. Формулы и алгоритмы из статей и
стандартов реализуем сами — идеи и математика лицензией не защищены, защищён текст кода.

### Электроника, микроконтроллер, поля, среда, радио (ночь 2) — что своё и почему

| Область | Своё на Rust | Внешний эталон | Почему так |
|---|---|---|---|
| Схемы | MNA-решатель `sim-circuit` | **ngspice 47** (BSD, процесс `ngspice -b`, собран из исходников в `assets/third_party/ngspice`) | схема должна шагать вместе с прошивкой и мотором каждые 25 мкс — внешний процесс в такой цикл не встанет; ngspice проверяет тот же нетлист |
| Микроконтроллер | `sim-mcu` для прежнего виртуального ABI, `sim-boards` для профиля платы и ESP32-C3 | RISC-V, кодировки LLVM и нативная логика для прежнего ABI; TRM и трассы QEMU для raw flash C3 | часы гостя ведёт рантайм. QEMU S3 работает отдельным диагностическим процессом |
| Прошивка | Rust `no_std`, rustc + rust-lld для старых сценариев; штатные образы ESP-IDF и Arduino для C3 | независящая от симулятора сборка SDK, трассы QEMU и расчёт времён из настроек | машинный код выполняется через контракт платы. Область сверки описана в §8.4 |
| Поля и магниты | `sim-em`: замкнутые формулы, эквивалентные токи, магнитная цепь | две независимые формулы на каждую величину; замер K&J; паспорта maxon/HD/CubeMars | 3D МКЭ (Elmer — GPL/LGPL, FEMM — своя лицензия) нужен только для сложных форм — этап позже, процессом |
| Тепло человека | `sim-env`: двухузловая модель Gagge (порт pythermalcomfort, MIT, с атрибуцией) | таблица ASHRAE 55-2020 (22 строки), тестовые значения pythermalcomfort | многосегментная JOS-3 (руки, пальцы отдельно) — следующий шаг |
| Радио | `sim-radio`: бюджет линии по измеренным моделям и пакетный канал Wi-Fi/BLE/ESP-NOW | ITU-R P.525/P.840, Klein–Swift, PSS-78, IEEE 802.15.6, даташит ESP32-C3 | интеграция на границе драйвера, физический уровень вне третьего ТЗ |
| ЭМС | `sim-circuit::emc`: сосредоточенные и локальные модели | openEMS 0.37, отдельный FDTD-процесс для трёх стендов; ngspice для RL и ESD | инженерная оценка в пределах заданных геометрии и частот (§8.4) |

## 4. Как источники соединяются

Цепочка экзоскелета **работает** в сценарии «Экзо целиком: прошивка в контуре» (обмен каждые
25 мкс, ~26× быстрее реального времени):

```
 телефон ──BLE (sim-radio: потери, задержки, разрыв)──▶ МК RV32IMC (sim-mcu, прошивка exo-ctrl)
    ▲                                                        │ ШИМ, направление, разрешение
    └──────────── телеметрия 50 Гц ◀─────────────────────────┤
                                                             ▼
 АЦП: угол, ток, температура корпуса, батарея ◀── H-мост (усреднённый) ── батарея 6S2P
        ▲                                             │ напряжение
        │                                             ▼
   локоть: масса и инерция предплечья ◀── момент ── мотор + редуктор + нагрев (sim-em)
   из MS-Human-700 (MuJoCo), груз, человек            ▲ охлаждение: воздух / ветер / вода (sim-env)
```

Исходный план связки (внешние движки через FMI и процессы) остаётся для тяжёлых
расчётов:

```
 прошивка (Renode) ──команда ШИМ──▶ драйвер (ngspice/своё) ──ток──▶ мотор+редуктор (FMU/своё)
        ▲                                    │                              │
        │ датчики (угол, ток, ИМУ)            ▼                              ▼ момент
        └──────────── сцена ◀────────── батарея (PyBaMM → своё)     шарнир экзо (sim-core)
                       │                                                    │
                       ▼                                                    ▼
          тело человека (sim-core + мышцы по OpenSim)          нагрузки на детали → прочность
                                                               (sim-fem, CalculiX процессом)
                                                               давление манжеты → FEBio
```

* **Время** ведёт наш оркестратор: фиксированный шаг механики (сейчас 0.5–1 мс), внешние
  модели шагают по FMI `doStep` со своим шагом, обмен — на границах.
* **Медленные/тяжёлые расчёты** (прочность в CalculiX, ткани в FEBio) идут не в цикле, а
  по событию: «сохранили пиковые нагрузки за сценарий → прогнали деталь → вернули запас».
* **Единицы — только СИ** внутри; переводы только на границе с внешним форматом.
* **Каждая связка — со своей проверкой**: энергия на стыке (электрическая мощность ×
  КПД ≈ механическая), согласованность единиц, сходимость по шагу обмена.

## 5. Сверка с эталоном — как проверяем каждую модель

Любая наша модель живёт в связке с **эталоном**, и эталон — независимый способ получить
то же число. Каждая сверка оформлена как `Check` (`sim-verify/src/check.rs`): оба числа,
абсолютная и относительная ошибка, допуск, чем получено каждое число, и допущения. Те же
проверки идут в `cargo test`, в отчёте `verify-report` и в окне (панель «Эталонные проверки»).

### Уровни эталонов

1. **Аналитика** — точная формула (период маятника через эллиптический интеграл,
   z = z₀ − g·t²/2, P·L³/(3EI)). Самое сильное доказательство, где применимо.
2. **Второй численный метод** — та же физика другим алгоритмом: МКЭ ↔ многотельная
   цепочка ↔ эластика (ОДУ); прямая динамика ABA ↔ обратная RNEA ↔ ручная сумма моментов.
3. **Внешний проверенный движок на той же модели** (этап 2+): наша RNEA ↔ MuJoCo/Pinocchio
   на одном MJCF; наша балка ↔ CalculiX на одном сечении; наша батарея ↔ PyBaMM.
4. **Эксперимент**: стенд (датчик момента на оси, весы, тензодатчики). Для всего, что
   касается тела, — обязательно, симуляция его не заменяет.

### Не только «ошибка мала», но и «ошибка ожидаема»

Проверяем, что знаем ошибку заранее:

* малые углы, 1°: симуляция расходится с 2π√(L/g) на **1.9e-5** — ровно поправка θ₀²/16,
  то есть это допущение формулы, а не ошибка движка;
* полунеявный Эйлер: ошибка падения совпадает с теоретической g·t·dt/2 до 1e-13, а при
  dt/2 падает ровно вдвое (первый порядок);
* цепочка из N звеньев: ошибка 1/(4N²) = 6.25e-4 при N = 20 — совпала с предсказанием,
  а при удвоении N падает ровно в 4 раза.

Если ошибка совпала с ожидаемой — модель понятна. Если ошибка меньше, но «непонятно
почему» — это тоже повод разбираться.

## 6. Конструктор и вердикт

`sim-device` описывает устройство, `sim-scenarios/src/device_assess` собирает вердикт из расчётных
крейтов. Единицы в файле проекта — миллиметры и градусы, в расчётах — СИ; перевод покрыт ручным
расчётом в `tests/device_constructor.rs`.

Правила вердикта:

* любой `Fail` даёт `Rejected`, неконечное число — тоже;
* `PassedSimulation` требует положительного доказательства в каждой из десяти групп и ни одного `NotAnalyzed`;
* `Readiness::BenchOnly` — отдельная шкала. Расчёт конструкции сошёлся, а незакрытое требует стенда
  (`needs_real_bench`). Она не ослабляет `verdict`;
* несущая деталь считается на паспортный пик привода: сбой прошивки не должен её ломать;
* значения вне физического диапазона (`physical_range`) отклоняются при разборе описания;
* замер привязан к отпечатку конструкции и образа прошивки (`design_stamp`).

Проверки: `tests/device_constructor.rs` (опасные устройства), `tests/device_sweep.rs` (порча каждого
поля от проходящего контроля), `crates/workshop/src/ui_tests.rs` (интерфейс настоящими событиями ввода).
Расхождения модели человека с измерениями — `sim_human::known_discrepancies`; защитные сверки
`human_verdict_*` требуют, чтобы вердикт не был оптимистичнее самих измерений.

### 7.3 Решения

1. **Новые крейты чисты по умолчанию.** `crates/sim-verify/tests/platform_boundary.rs` запрещает имена
   устройств в любом крейте вне списка старых. В старых коде счётчик по каждому файлу только падает:
   сейчас 963 упоминания в 38 файлах, цель 0 вне анатомии.
2. **Анатомия не устройство.** Слова вроде «локоть» допустимы только в `sim-human`, потому что человек
   участвует в любой сцене. Названия устройств запрещены и там.
3. **Контроллер не видит истину на уровне зависимостей.** `sim-control` не зависит от `sim-runtime`,
   `sim-mujoco` и `sim-world`. Контроллер получает только `Observation`. Тип `Truth` создаётся в
   `sim-runtime` и передаётся только оценщику.
4. **Время целочисленное.** Шкала в наносекундах, момент k-го такта равен `⌊k·10⁹/f⌋`, без накопления
   ошибки. Порядок внутри одного момента фиксирован: физика → датчики → связь → контроллеры → приводы.
5. **Детерминизм.** Один поток на прогон, устойчивый порядок, генераторы `sim_signal::Rng` из зерна
   мира и имени компонента. Часы компьютера доступны внешнему координатору для бюджета (§7.8).
   Лог хешируется побитово.
6. **Снимок и ветвление.** Снимок содержит полную копию `mjData` (`mj_copyData`) и клоны всех компонентов.
   Ветвь получает собственные данные и не меняет основной мир.
7. **MuJoCo считает контакт и многотельную динамику, `sim-core` проверяет.** Скомпилированная сцена
   сверяется по массам, инерциям и моментам.
8. **Файлы данных: TOML со строгим разбором.** Неизвестное поле является ошибкой. У каждого числа каталога
   есть источник. Формат `.device` версии 2 открывается через миграцию.
9. **Старое живёт, пока новое не доказано.** `ExoLoop` остаётся оракулом до сдачи этапа 3. Перенос
   сравнивается с `golden/exo_loop` с допуском 1 %, затем код под устройство удаляется.
10. **Контракт платы.** `BoardSim` обслуживает встроенные модели, включая виртуальный ABI,
    прежние ELF/HEX и raw flash C3. Диагностический QEMU S3 подключается через отдельный
    адаптер с открытым обязательством по повторяемости (§8.4).

### 7.4 Что считается правкой ядра

Деталь, устройство, прошивка, задача и новая комбинация моделей задаются только данными. Новая архитектура
процессора или новый класс физики действительно требуют Rust. Это расширение платформы общим механизмом,
и после него заново прогоняются все контрольные устройства.

### 7.5 Эталоны

`golden/exo_loop`: 11 режимов (6 штатных и 5 отказов), шаг 25 мкс, отпечаток по всем шагам и редкие
отсчёты 5 мс. Тест `sim-scenarios/tests/golden_exo_loop.rs` требует побитового совпадения. Перезапись
только явно, через `UPDATE_GOLDEN=1`.

### 7.6 Камеры

Кадр считает свой программный растеризатор, а не GPU. Причины: побитовая воспроизводимость, работа при
заблокированном экране и точная проекция для приёмки. Цвет упрощён и помечается в результате, поэтому
успех зрения на таком кадре не закрывает опасность без проверки на настоящей камере.

Пуассона относится к модели плоского напряжённого состояния. Передача нагрузки
на произвольное сечение, концентраторы и непрерывная огибающая требуют отдельного подтверждения.
У приводной сборки в контакте с участником высшую ступень закрывают только заверенные
натурные проверки каждой обязательной опасности. Предел ткани применяется к подтверждённой
длительности контакта. Дискретный резерв, ток и температура относятся к своему стенду. Для утверждения
готовности железа требуются подтверждённые тепловые параметры проводки, огибающие привода
и ячейки, срабатывание защиты, область применимости реального монтажа,
подтверждение цепочки поставки и отпечаток установленного образа на физической плате.

**Этап 7. Связь с реальностью.**

`sim-reality` импортирует каналы в `SignalTable`, наблюдения в `Sample`, команды в
`Command`. До запуска проверяются единицы, сетка, конечность, номера до транспорта
и завершённость журнала. При воспроизведении `Runtime::act` применяет команды в нуле
до событий, а на последующих метках после совпадающих событий.

Идентификатор использует баланс усилий вне страгивания, наклоны нагруженных сторон
передачи, разность парных меток и модель Брауна — Конради для известной мишени. SVD
масштабированного якобиана проверяет вырождение и даёт чувствительность и
обусловленность. Интервалы включают шум, остатки и, для задержки, границу ошибки часов.
Независимая приёмка этапа 7 проверила 15 параметров на трёх шумовых сериях. Максимальная
ошибка 0,558075%, расхождение проекции до 0,025003 px. Установка задержки 174 мкс
сдвинула доступный отсчёт на 3 мс с 15 до 9 мкм при сверке с ручным балансом.
[Исходная приёмка](docs/STAGE7_NOTES.md).

`sim-cli` применяет `MeasuredCapture::verify` к исходным байтам и записи владельца.
`CampaignEvidence::record_measurement` получает подтверждённый канал после живого
прогона с совпадающими ревизией, отпечатком сборки, полным `RunKey` и горизонтом.
`Verification::Measurement` оценивает ряд по окну и пределу установки. Синтетический
источник, другая ревизия, отсутствие заверения и пропуски ведут к явному отказу импорта
в вердикт. Пределы и требования кампании принадлежат её установке.

#### Чего пока нет на этапе 7

Натурный журнал и независимая сверка на физическом образце пока отсутствуют. Нужны
совпадение монтажных осей, единиц, шкал, временных меток и начального состояния,
а также обоснованные пределы с учётом погрешности измерительного тракта. Запись
владельца удостоверяет происхождение, а FNV-1a проверяет привязку к байтам. Проверка
подписи, регистратора и применимости калибровки к реальному стенду остаётся открытой.

**Этап 8. Клиент общего конвейера.** Исправления курсора внесены.

SIMVIEW v1 хранит JSON-описание фактически запущенного MJCF с установочными кадрами
датчиков, версией MuJoCo и схемой усилий. За описателями следуют байты пикселей и
исходный SIMLOG. В SIMLOG остаются наименования и единицы координат, наносекунды,
зерно и потактовые позы. Контрольная сумма пакета и отпечатки модели, журнала
и записанных изображений сверяются при чтении. Запись включается до первого такта
и переносится снимком и ветвлением. Отрисовщик загружает сцену и восстанавливает
позу из журнала. Вид датчика использует доставленные пиксели или ряд наблюдений
и измерений процессов с единицами и шкалой времени. Пропуски показаний дают разрывы,
а после конца любой из записей в сравнении её отсчёт отсутствует. Для модели без
поверхностей звеньев обзор показывает положения тел, их связи и центры масс из
восстановленной позы MuJoCo. Схема подписана в интерфейсе.

У пространственных реакций есть мировой вектор силы и момента и границы интервала.
Контактный вектор относится ко второму геому в позе левой границы интегрирования.
Для weld сохраняются реакции на обеих сторонах. События креплений несут времена
запроса и рассмотрения либо применения. В одиночной задаче есть диагностический
переход к максимуму ряда или контактной реакции. Для позы берётся
последний записанный физический такт на этой отметке. Отсутствие события или
кадра видно в клиенте. Пакет и диагностический максимум не участвуют в вердикте.

Семь штатных задач проверены двумя запусками. SIMLOG и JSON совпали побайтно
при записи для клиента и без неё. В 21 обзорной текстуре поза сверена с исходными
координатами, а видимые пиксели цели проверены обратной проекцией и радиусом MuJoCo.
Проверены 35 векторов реакций, восемь переключений связей в одном прогоне
и 16 доставленных RGB-кадров двух датчиков. Сверка девяти поз номинальной посадки
на трёх сценах дала невязку до 4,163·10⁻¹⁷ м.

Строка кампании хранит привязку к `RunKey` дочернего опыта и отдельно указывает
фактическую сетку, вариант, зерно, границу журнала и его отпечаток. Оценщик привязывает
нарушение по отпечатку того журнала, который его зафиксировал. Среди завершённых
дочерних опытов приоритет у более тяжёлого исхода. При равных исходах выбирается опыт
с привязанным нарушением. Если у оценщика нет события в выбранном журнале,
строка сохраняет пустую отметку, а окно показывает причину.

Повтор связанного профиля заново исполняет выбранный дочерний опыт для выгрузки.
Оригинальный отпечаток журнала, горизонт, зерно и входы проверяются до публикации
пакета. SIMVIEW сохраняет привязку и вердикт отчёта повтора. Workshop сверяет привязку
с исходным отчётом, если он открыт, и переходит к метке события в целых наносекундах.
`--log` позволяет независимо выгрузить байты того же повтора без записи просмотра.
Невыполненная строка сообщает причину через `view_unavailable`.

Тест Workshop открывает худшую строку каждой из семи сборок манифеста этапа 6.
Он сверяет 21 текстуру 480×360, позы, проекцию геометрии и семь пар SIMLOG с записью
просмотра и без неё. Если есть временная метка нарушения, курсор стоит на ней.
Иначе пакет открывается на нуле и показывает отсутствие события. На общих 30 мс парных
задач отсчёты совпали,
а на 37 000 003 нс длинная запись показала 7,030 мм по сумме шагов Euler. Короткая
запись к этому моменту закончилась.

#### Чего пока нет на этапе 8

Часть критериев оценивает весь интервал или сводку сеток. Если оценщик не привязал
событие к отсчёту, окно явно сообщает об отсутствии отметки. Геометрия и движение
участника относятся к номинальной модели. Фактическая
посадка, давление и индивидуальная пригодность для носки остаются `NotAnalyzed`
до обмеров владельца и независимой калибровки.

### 7.8 Покрывающие кампании третьего ТЗ

`depth_factors` сценария задаёт конечные уровни, совместимость и признаки безопасности.
`sim-task::campaign::{depth_factors,depth_cover,depth_search}` разрешает допустимые строки,
покрывает пары и тройки безопасности и предлагает соседние уровни по нормированному запасу,
если подтверждены предел, окно и масштаб. `[coverage]` установки связывает план с режимами и
профилями. `sim-cli::tasks::campaign` разрешает мир, профиль, инъекцию, сетку, зерно и горизонт.
Квитанция фактического запуска связывает входы, применённый отказ и SIMLOG с `RunKey`.
Только подтверждённые строки входят в выполненное покрытие.

Внешний координатор `sim-cli` резервирует запуски и останавливает работы по дедлайну.
Часы координатора управляют бюджетом, время моделей идёт по целочисленной шкале.
В лимит каждой установки входят дочерние и сравнительные запуски, уточнение и приёмочный
повтор. Контрольная точка хранит состояние бюджета `depth-budget-v1.json` и квитанции.
В `depth_coverage` публикуются `required/planned/executed` по парам и тройкам, открытые строки,
худший ключ, резерв, подтверждённые запуски и итог повтора. Прежние манифесты сохраняют
старый маршрут. [Форматы и совместимость](docs/DEPTH_MIGRATION.md).

```sh
cargo run --offline -p sim-cli --bin sim-run -- --campaign devices/depth-campaign.toml \
  --checkpoint "$DEPTH_CHECKPOINT" --jobs 2 --json
cargo run --offline -p sim-cli --bin sim-run -- --campaign devices/depth-campaign.toml \
  --checkpoint "$DEPTH_CHECKPOINT" --repeat "$RUN_KEY" --view worst.simview --json
```

Повтор использует ту же контрольную точку и сборку `sim-run`, а `RUN_KEY` берётся из
`assemblies.<номер>.worst_run_key`. На семи установках оракулы по ключам
и проекциям подтвердили **122/122 пар и 107/107 троек безопасности**, повтор — **7/7 SIMVIEW**.
Лимит 1000 запусков и 30 минут на установку соблюдён в финальном опыте. Первый запуск занял
192,26 с, максимальное время установки — 148,184 с. Второй отчёт совпал без поля
фактического времени. Поиск по нормированному запасу сверен на каретке. Для семи сборок
физический худший случай и непрерывная огибающая остаются `NotAnalyzed` до измерений.
Сохраняются 22 исторические строки этапа 6 с ключами и причинами. Полный перебор за границей
§5. [Финальная сверка](docs/DEPTH_BACKLOG.md#т7--кампании-и-покрытие),
[адресный тест](crates/sim-cli/tests/depth_campaign.rs).

## 8. Электрический слой

Слой общий для любых устройств и работает без окна. Схемы решает `sim-circuit`.
Электрическая модель вывода пользуется `PinSpec` из `sim-boards`. Переходы и дребезг контактной
ветви опираются на `sim-process::work::ElectricalContact`. Имена устройств и их прошивок остаются в данных.
[Электрический контракт](docs/ELECTRICAL_SPEC.md), [план второго ТЗ](docs/ELECTRICAL_PLAN.md),
[третье ТЗ](docs/HARDWARE_DEPTH_SPEC.md).

### 8.1. Граница данных и расчёта

- `sim-world` читает необязательную ссылку `schematic` относительно файла устройства. Загрузчик отдаёт
  разрешённые пути по именам экземпляров рядом с `CompiledWorld`. Форматы импорта и миграция дают
  пустую ссылку. `CompiledWorld` и контракт `sim-signal` сохраняются.
  При загрузке только физического мира заявленная схема оставляет открытое доказательство.
- `sim-cli::electrical` строго читает версионированные TOML и сохраняет фактические байты схемы и
  каталога. Установщик передаёт разрешённые экземпляры, физические контакты платы и функции.
  Номер канала АЦП или ШИМ разрешается в контакт по каталогу и настройке мультиплексора.
  Байты входов и идентичность схемы входят в отпечатки установки. Живой опыт привязывает
  профиль, горизонт и журнал к этой установке. Типизированный повтор сверяет ту же идентичность.
- `sim-process::schematic` владеет типизированными выводами, моделями, цепями, монтажными
  связями, источниками `SourcedRange` и пределами. Имена цепей предназначены для сверки монтажа.
  Ток идёт по элементам и фактическим соединениям, каждое из которых сохраняется отдельной
  ветвью. Эквиваленты раскрываются в `Netlist`, обратная карта адресует выводы и элементы
  исходной схемы. Несовместимые контакты размыкают ветвь и дают `assembly_mismatch`.
- Для `missing_ground` нужен физический штатный путь от локальной опоры приёмника к опоре
  отправителя. Численная опора, защитная ветвь и ключ с неподтверждённым состоянием такой путь
  не доказывают. Для `reverse_polarity` знак берётся в порядке маркированной пары `V(+) − V(−)`
  и сравнивается с применимым обратным пределом. Между плавающими опорами разность в DC
  остаётся неопределённой. Независимые острова считают со своими опорами и без численных шунтов.
- Сборочный лист опирается на тот же граф, включая порядок операций из данных и адреса концов.
  Проверки без питания отделены от первого включения с ограничением тока. Неустановленный
  параметр сопровождается замером. Синтетические эталоны помечены отдельно, их выводы
  имеют область применения только в расчётной постановке.

### 8.2. Расписание, доказательства и приёмка

- На Э2 применимость выводится из схемы для девяти режимов §3.5. Открытые огибающие остаются
  `NotAnalyzed`, случайные серии есть только в режимах 6 и 7. Одиночный обрыв адресует физический
  провод. Для DC принят допуск
  `max(10 мВ, 1% |Vref|)`. Пик и время установления сравниваются в общем окне с допуском 5%,
  полоса и исходное состояние задаются опытом. Полный корпус требует фактического запуска ngspice.
- На Э3 `sim-runtime` на общей целочисленной шкале закрывает электрический интервал с
  удержанной нагрузкой и затем публикует питание на следующий интервал. Плата и приводы
  получают напряжение относительно своей опоры и возвращают знаковый ток. Пересечение порога
  с выдержкой вызывает сброс той же платы. Снимок и ветвление сохраняют состояние цепи,
  переключений и планировщика. Контроллеры получают штатные наблюдения, электрическая истина
  доступна оценщику. Сокращённая шина допустима после измеренного замедления более 2× и сверки
  событий и огибающих с полной цепью.
- На Э4 `sim-task` выводит обязательства из состава и применимых режимов и сохраняет смысл
  `Finding` и `Readiness`. Два токовых кода остаются причинами `Overcurrent`, `WiringHeat`
  сохраняется отдельным обязательством. Неприменимость выводится из состава схемы и попадает
  в `inapplicable` как `NotApplicable` с причиной и источником. В `Scope::Assembly` проверка
  потенциально опасной схемы остаётся `NotAnalyzed`, если вывод зависит от непроверенных параметров,
  пределов или условий режима. Отсутствующая схема, неполный интервал или пропущенное наблюдение
  также оставляют обязательство открытым. Подтверждённое нарушение сохраняет `Fail` при открытых
  соседних обязательствах. Неконечные параметры, конфликтующие привязки, неизвестные ссылки и поля
  относятся к ошибкам входных данных.

### 8.3. Приёмка электрического слоя

получает `Fail` по целевой причине и итог `Rejected`. Исправленный эталон получает `Pass` по
целевой причине в пределах стендового опыта, общий итог остаётся `NotProven`.

с текстом «Исходная спецификация стенда Э2» обозначает синтетические пределы корпуса, применимые

#### Чего пока нет в электрическом слое

- **Схемы и экземпляры.** Для семи сборок нужны сверка условных позиций и ревизий жгута
  с экземпляром, четырёхпроводные замеры сопротивления
  стыков, тепловые параметры участков и огибающие допустимого тока по длительности.
- **№1.** Нужны соответствие выводов виртуального ABI физической плате и аварийному входу,
  ревизии мотора и драйвера, BMS, предохранитель, разводка Холлов и путь рекуперации. Открыты
  нагрузочная и обратная ВАХ по заряду и температуре, пороги отключения и повторного пуска
  моста и фронты коммутации. Причинную проводку платы нужно сверить с выборкой конца такта.
- **№3.** Нужны конкретные батарея, контроллер BLE, камера, её разъём, шина и питание.
  Для датчика нужны токи VDD и VDDIO, переход питания и первая достоверная выборка IMU.
- **№4.** Нужны параметры источника, регуляторов, защиты, ключа и аналогового тракта,
  входной ток и импульсный интерфейс штатной сервы. Для `rail_sag` нужен синхронный журнал
  VDD, CHIP_EN, управляющих выводов и токов на конкретной плате с тем же образом, с порогом
  и выдержками сброса. Живой опыт подтверждает работу численного детектора.
- **№2, №5, №6 и №7.** Для №2 нужны параметры ячейки, BMS и моста, ток и изгиб жгута.
  Для №5 — пиковый ток и фронты интерфейса камеры и переход питания датчика угла.
  Для №6 — тепловая отсечка и сопротивление контактов сменной оснастки под нагрузкой.
  Для №7 — просадка, рекуперация и остаточный ток при одновременном пуске и реверсе.
  [Замеры по семи сборкам](docs/DEPTH_REPORT.md#ж--сборочные-листы-и-вывод-о-железе).
- **Пределы и свидетельства.** Открыты направленные пределы обратного тока и остаточного
  питания, условия параллельного включения, огибающие пуска, заклинивания и отключения,
  импульсные и тепловые пределы ключей. Требуются типизированная привязка ветвей, контактов,
  профилей платы и каналов журнала, а также граница экстремума между тактами для произвольных
  реактивных цепей.
- **Рантайм и инструменты.** В бэклоге фиксация тока нагрузок в общем планировщике,
  типизированный дисковый повтор, полнота отпечатка сборки, защита от чрезмерных подшагов RK4
  в прежнем пути батареи, отказ при переполнении в разборе SPICE и экспорт диода с `AREA=`.
- **Дальнейшие работы.** Редактор схем и показ проводки в 3D, внешняя автотрассировка,
  антенны и расширенные стендовые испытания. Открытые вопросы новых моделей перечислены
  в §7.8 и §8.4. [Бэклог электрического слоя](docs/ELECTRICAL_BACKLOG.md),
  [бэклог третьего ТЗ](docs/DEPTH_BACKLOG.md).

### 8.4. Третье ТЗ. Потоки данных и сверки

#### А · Образы плат, профили сброса и расход энергии

`sim-runtime/src/control/{schema,install,board}.rs` устанавливает `BoardSim` из графа управления:
прежний `image` принимает ELF/HEX, а сочетание с `flash_profile`, `rom` и `efuse` выбирает
строгий режим raw flash. В `sim-boards` модули `image`, `esp_rom`, `esp_clock` и
`peripheral::esp_*` ведут ROM → загрузчик → приложение, такты, MMIO, шины и IRQ.
В стендах `BoardSim::load_esp_flash_with_profile` явно принимает `EspProfiledBootOptions`.
Базовый профиль QEMU содержит 22 записи, дополнение I/O — 9. Отдельный
профиль RTC CRC описывает незавершённую операцию. Журнал `esp_reset_value_uses()` подтвердил
использование всех 22 базовых значений в `esp_sdk_boot`. Профиль и виртуальный RNG оставляют
аппаратное доказательство открытым.
[Таблица значений и источников](crates/sim-boards/SUPPORT.md#профиль-qemu).

На ESP-IDF 6.1.1 BoardSim и QEMU 9.2.2 достигли `app_main` по `0x42006bda`
на инструкциях 23 126 662 и 2 403 358 соответственно и выдали `Hello world!\r\n`.
В BoardSim строка видна к опросу на 233 мс. Строгий запуск без профиля остановился с
`UnsupportedRegister` при чтении `UART_STATUS_REG` (`0x6000001c`, PC `0x4004c0d4`, инструкция №6196).
Arduino ESP32 4.0.0 дал 1000/1005/1000 тиков между фронтами,
QEMU подтвердил записи MMIO. ESP-IDF проверяет GPIO (20 мс), UART1 (байты
`55 a6 00 ff` и интервалы в допуске 6,25 нс), LEDC (250 мкс, высокий уровень
62,5/187,5 мкс) и I²C (SCL 10 мкс, запись и чтение с repeated START за 475 мкс).
Сверки опираются на настройки SDK, TRM и покрытые трассой операции.
[Отчёт А](docs/DEPTH_REPORT.md#а--штатные-образы-и-контуры).

Пакеты от `sim-boards::esp_radio` идут через плату в `sim-radio::timed` на границе драйвера.
`power_profile` и `power_schedule` передают паспортные токи и длительности в
`sim-process::schematic::mcu_energy`. Результат — модельный заряд. Для автономности нужна
батарея с измеренной нагрузочной кривой, токами регулятора и утечек. Каталог задаёт
S3 N16R8 (16 МБ flash, 8 МБ PSRAM), OV2640 на U3359 и заявленные 1000 мА·ч Li-Po
803040 с открытыми параметрами ячейки. [Каталог](catalog/electrical/).

`sim-runtime::control::external_board` запускает QEMU S3 отдельным процессом.
Два запуска повторили UART0 ROM и SLIP SYNC 46 → 14 байт. Установщик CLI получил 107 байт
до приглашения загрузчика. Сцепление с виртуальным тактом, снимок, питание и полный контур S3
остаются `NotAnalyzed`. У C3 этот статус сохраняют холодный старт на кремнии, электрические
фронты, ADC1 без заводской калибровки, штатный deep sleep, пробуждения по таймеру и GPIO
и wake stub. Регистровые тесты RTC, SPI2/GDMA и WDT имеют отдельную область.

```sh
SIM_ESP_ACCEPTANCE_ROM=/путь/к/esp32c3-rom.bin \
  cargo test --offline -p sim-boards --test esp_sdk_acceptance -- --include-ignored --test-threads=1
SIM_EXTERNAL_BOARD_QEMU=/путь/к/qemu-system-xtensa \
  cargo test --offline -p sim-runtime --test external_board qemu_uart0_rom -- --ignored
```

#### Д · Реестр и путь доказательства

`sim-task/src/verdict/{registry,evidence}.rs` добавляет ровно 11 кодов в реестр v3.
`sim-cli::electrical::report` публикует `depth_checks`. Свидетельство связывает предел и ряд
с ветвью, окном, ревизией и инъекцией. `Finding.depth` сохраняет отпечаток наблюдения,
источник применимости и привязку события. Общий вердикт получает обязательства
из состава и режима. Если применимость, предел или межтактовая огибающая открыты,
проверка остаётся `NotAnalyzed`. Подтверждённый `Fail` ведёт к `Rejected` даже
при соседних открытых проверках. Группы `Overcurrent` и `Battery` сохраняют прежний смысл.

| Код расчёта | Классы |
|---|---|
| `sim-process::schematic` | `capacitor_stress`, `fuse_coordination`, `switch_thermal`, `deep_discharge`, `sleep_drain`, `esd_event`, `emi_reset` |
| `sim-process::work`, `sim-process::schematic::solder_joint` | `cable_flex`, `solder_defect` |
| `sim-circuit::pcb` | `creepage_clearance`, `ground_bounce` |

У 15 опасных вариантов адресный `Fail`; исправленные варианты выполняют стендовый
критерий. Пайка и ЭМС сохраняют ограничения из предыдущего раздела. Сверка I²t дала
запас провода −10…−5 → +3…+8 мс, а EMI дал 1,8 → 2,2 В при пороге 2,0 В и
сброс/отпускание на 19/25 мкс только у опасного варианта.
